# 归档图片编辑框架设计对比与借鉴分析

> 日期：2026-10-08 · 前置文档：《iOS开源视频剪辑框架选型调研报告.md》（倾向采用 Kadr）
> 本文回答一个问题：**在开始基于 Kadr 开发之前，归档目录下的图片编辑框架有哪些设计可取之处值得带入新项目？**
> 对比对象：`归档/code` 下的 ImageEditorOC（原生库）、imageEditor_js（RN 业务配套层）；
> ImageEditorResource 只是 SVG 模板资源包，不构成框架，不参与对比。

---

## 一、三个对象的本质差异

| | ImageEditorOC | imageEditor_js | （参照）insedit |
|---|---|---|---|
| 是什么 | 图片编辑**能力库**（涂鸦/马赛克/贴纸/裁剪），为 RN 服务 | 高德 RN bundle 的**业务层**：路线 SVG 合成、模板解析、水印云控 | 跨端视频剪辑 SDK，生产级，背负演进债 |
| 内核风格 | 不可变值语义 Model + 快照撤销 + 轻状态 native 层 | 单例 + 可变状态分散在各模块（Watermark / CacheService / OperationCache） | 可变内核 + MVI 外壳缝合 |
| 完成度 | Demo 级，架构意图清晰、有完整设计文档 | 生产代码，业务驱动，无架构文档 | 生产级，2900 文件 |
| 对新项目的价值 | **正面教材**：设计决策均有文档化的意图与边界 | **反面教材 + 工程细节**：状态分散的教训、云控/性能画像可借鉴 | **债务警示**：每条债对应一个可预防的坑 |

关键背景：ARCHITECTURE_COMPARISON.md 已经把 ImageEditorOC 与 insedit（视频剪辑，正是新项目要建的同类系统）
做过一次同标尺评审，核心结论是 **insedit 的主要债务可追溯到一个起点——内核没有坚持不可变、单一表达的 Model**。
而新项目的候选 Kadr，其 DSL 树恰好就是不可变值类型——这意味着 ImageEditorOC 的多数核心决策与 Kadr 同构，
借鉴的方向不是"修补 Kadr"，而是**把已验证的设计直觉在新项目的 App 层（Kadr 之上）落地，并提前布置防线**。

---

## 二、值得借鉴的设计（按优先级）

### P0-1. 快照即撤销：撤销栈建立在不可变树上，而不是命令逆操作上

ImageEditorOC 的决策：所有编辑状态是纯数据数组，Model 全值语义，因此**不内置撤销栈**——
撤销退化为"JS 层保存 Model 快照数组，undo/redo = 移动数组下标"。命令模式被"状态可整体快照"消解，
复杂度不随操作类型增长。

Kadr 侧的天然优势：DSL 树（Video/VideoClip/Transition/AudioTrack/Filter）本身就是不可变值类型，
且 kadr-persistence 已经提供序列化。**新项目应做的**：

- 编辑历史 = `EditPlan[]` 快照栈（或直接存 DSL 树引用，Swift 结构体拷贝廉价）
- 不做 Command + 逆运算；不做"基线快照 + 命令重放"（insedit 的 undo 漂移之源）
- 快照策略（步数上限、内存裁剪）由 App 层决定，引擎保持无感知
- 快照栈可直接架在 kadr-persistence 的格式上：持久化草稿与撤销历史同源，一份 schema 两个用途

### P0-2. 坐标系锚点：交互数据永远存"素材/时间线坐标系"，不存屏幕坐标

ImageEditorOC 的根基性决策：编辑中 view 会被缩放、旋转、裁剪，**数据层永远存储图片坐标系**，
基类用 8 个双向转换方法收拢全部坐标变换；任何 View/手势处理禁止直接存 view 坐标到 Model。

泛化到视频剪辑是**两套坐标**：

- 时间轴坐标：一切时间数据存"时间线绝对时间"或 Kadr 已采用的"片段相对时间"，不存播放器 currentTime
- 空间坐标：贴纸/字幕/水印位置存"输出画幅坐标系"（归一化 0...1 更稳），不存预览 view 的像素坐标

Kadr 的关键帧已按片段相对时间定义，与图片库"数据不随 view 状态失真"是同一设计直觉——
App 层自研 UI（贴纸拖拽、字幕定位）时必须守住这条，这是最容易被 SwiftUI 手势代码悄悄破坏的地方。

### P0-3. 概念表达份数判据：给 Kadr 的演进装上计数器

ARCHITECTURE_COMPARISON.md 提出的通用判据：**数"同一个概念的表达份数"**——表达份数 ≈ 转换器数量
≈ 一致性 bug 的藏身之处。insedit 的"旋转"在全库有 6 个以上字段、fps 出现 Double/Int 类型漂移，
而 ImageEditorOC 的"笔迹""贴纸"均只有一份表示。

新项目的用法：把这条判据变成 Code Review 的显式问题——"这个字段是全库第几份表达？"
Kadr 侧已知的好消息：预览（`makePlayerItem`）与导出（`export`）共用同一套动画驱动，同源原则在引擎层已成立；
要盯的是**自己写的 App 层**别在 DSL 之外平行生长出第二套参数（如一份"UI 编辑状态 JSON" +
一份"导出配置"，靠转换器同步）——这正是 insedit 五层模型的覆辙。

### P1-1. 预览态继承扩展，而不是平行复制

ImageEditorOC 的方案：`HYImageCompositorItem`（纯数据，导出用）← `HYImageCompositorViewItem`
（+ selected/dragging/exchangeTarget，预览用）。预览数据是编辑数据的**严格超集**，继承精确表达关系：
概念表达份数 = 1，零转换器，导出按基类切片合成。

对 Kadr 项目的映射：**不要往 DSL 树里塞 UI 态**（selected、dragging、当前选中转场高亮）。
做法是在 App 层定义 `EditorClip: 包装 Kadr 的 VideoClip + UI 态` 的超集结构，导出/持久化时切回 DSL。
这样 kadr-persistence 的 schema 不被 UI 字段污染，kadr 升级时 App 层改动面最小。

### P1-2. 编排层独立：跨模块事务不进场景门面

对比文档 4.5 节的教训：insedit 的场景 Module 变成 5115 行 God Object，因为跨 Editor 的编排
（裁剪联动 BGM/转场/画中画/撤销分组）没有独立去处。

新项目建议预先把 App 层切成三层：

```
EditorView（薄：装配/绑定/生命周期，SwiftUI）
  → EditUseCase 层（跨模块事务、撤销分组、联动规则，场景无关）
    → Kadr DSL 树 + kadr 引擎
```

典型归属测试（沿用对比文档的判据）："加转场并联动音频 ducking"这类动作换个场景仍然需要，
就不该长在任何一个 View 里。

### P1-3. 轻状态引擎 + 状态持有者在 App 层

ImageEditorOC 的定位决策：native 层保持轻状态、可快照，编辑状态持有者是 JS 层。
Kadr 已经做对了一半（引擎层 internal、状态即 DSL 树）。App 层要补的纪律：
播放器的 currentTime、预览缩放、面板开关等**瞬态**不进持久化模型；
撤销分组边界（一次"操作"的定义）在 UseCase 层显式声明，而不是散落各 View。

### P2-1. YAGNI + 显式演化预案的写法

ImageEditorOC 决策 7 的格式值得原样借用：**触发条件写明的预留演化路径**——
"笔刷达到 3 种以上时启动策略协议抽象"，并附届时怎么改（字符串类型 → NS_STRING_ENUM，分发 → 注册表）。
AI_ERASER_MVP.md 则记录了验证过程：第 3 种笔刷（Eraser）到来时按预案执行抽象，
新增笔刷 = 一个策略类 + 一行注册，不改既有代码。

对视频项目的翻译：为"能力注册表"预留同一位置——滤镜、转场、AI 工具的接入点统一走注册表
（`[CapabilityID: Strategy]`），第 1、2 个能力可以 if-else，**触发条件写进设计文档**，
第 3 个到来时必须抽象。AI 剪辑 Agent 本身就会是"第 N 种消费者"，注册表正是 Agent 工具枚举的挂载点。

### P2-2. 渲染职责剥离 + 参数级 diff 的思想

图片库的渲染演进路线：先剥离 Model 的绘制职责，再谈 GPU 管线，顺序不可颠倒。
视频侧对应物 Kadr 已具备（Model 只存参数、渲染全延迟到引擎），无需重做；
但有一条图片库自己的妥协可反向学习：笔迹按"桶"增量刷新（马赛克 10 条/桶、画笔 20 条/桶）
是粗粒度 diff——insedit 的 RenderParams Differ 是细粒度 diff。
新项目若自研预览层组件，刷新粒度以参数 diff 为起点，不必经过"分桶"这一代。

## 三、可借鉴的工程细节（imageEditor_js 侧）

图片 JS 业务层架构上无甚可取（单例 + 分散可变状态，恰是 ImageEditorOC 决策的反面），
但有三处工程实践可直接搬：

| 实践 | 出处 | 搬到视频项目 |
|---|---|---|
| 云控水印：水印样式走云端配置下发，按 styleType 索引，支持仅预览/导出双开关 | Watermark.js | 水印/片头片尾能力云控化，side project 阶段也能不发版换样式 |
| 性能画像：模板应用等关键路径打 scene 级耗时埋点（InfoPerfLog） | ImgCompositorCacheService.js / PerformanceProfile.js | 预览首帧、导出耗时两条关键路径从第一天埋点 |
| 素材缓存服务：zip 模板下载-解压-缓存统一管理，带失效路径 | ImgCompositorCacheService.js | 贴纸/LUT/字幕字体等素材包的下载缓存同一模式 |

反面条纹同样要记录：imageEditor_js 的 `ImageEditorOperationCache.js` 注释写着
"未来用于管理 undo/redo 数据"——**一个从未兑现的 undo 占位符**，且状态分散在 Watermark 单例、
CacheService 单例、各 page 的 model 里。这与 ImageEditorOC"状态集中于数组、快照即撤销"形成对照：
undo 不是某个缓存模块的职责，而是**状态建模方式**的副产品。新项目若撤销做不顺，第一反应应是
检查状态是否值语义、是否单一数据源，而不是去补一个 undo 模块。

## 四、不建议带入的做法

1. **全局通知直达最外层**：图片库为零转发层 + RN 桥接成本做的取舍（NSNotification 一跳直达）。
   纯 Swift/SwiftUI 项目无此约束，用 Observation / delegate 即可，可发现性和编译期检查都更好。
2. **KVO 手动转发**：图片库自己标注的已知脆弱点（对 keyPath 拼写敏感）。Swift 侧无必要。
3. **Model 承载绘制职责**：图片库唯一公认的职责越界（`HYImageCompositorItem` 持有 CoreGraphics 绘制），
   其演进路线第一步就是抽离它。Kadr 的 Model 已不带渲染，保持即可。
4. **继承解决多层问题**：ViewItem:Item 只优雅地解决"数据 + 一种预览"两层；
   N 层场景的正解是单一权威参数树 + 边界一次投影（Kadr 的 DSL → 引擎投影已是这个形态）。
   不要把它当成通用分层手段滥用。

---

## 五、结论

归档框架对新项目最大的价值不是代码，而是**一组已被文档化、且经跨项目对照验证过的设计直觉**：

1. 不可变 + 单一表达的内核，是撤销、持久化、预览导出同源、Agent 可读四个问题的共同解——
   Kadr 在引擎层已满足，**风险全部转移到 App 层**，上表 P0/P1 各项就是防线。
2. 把"概念表达份数""编排动作归属测试""预留抽象的触发条件"这三条判据写进项目的
   Code Review checklist，成本极低、防的正是 insedit 级别的债。
3. 落地建议：在 POC 阶段就按 P1-1（超集包装 UI 态）和 P1-2（三层切分）搭骨架，
   两者在 side project 早期几乎零成本，后期再补就是重构。
